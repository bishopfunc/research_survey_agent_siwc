# ADR 0026: 手法の分類の軸をDSLの項目として持つ

状態: Accepted
日付: 2026-10-14 JST
関連design doc: [0038](../design/0038-integrated-tutorial-style.md)

## 背景

ユーザー指示（2026-10-14）「手法の分類の軸を構造（DSLの項目）として持つ」。[0038](../design/0038-integrated-tutorial-style.md) は、地図表現の研究動向の記事に倣って、分野の分類の軸（機能・表現・方式・入力）を決め、中心の軸に沿って系統を並べる。最初の実装では軸を系統の説明の文に書くだけで、画面で軸ごとに並べることも、抜けを点検することもできなかった。

## 判断

- 分野（Domain）に任意の `classification_axes` を足す。軸ごとに `id`・`label`（日本語の軸の名前）・`kind`（`function` 機能・`representation` 表現・`approach` 方式・`input` 入力・`other`）・`description`・`central`（中心の軸。1つの分野で多くとも1つ）を持つ。最大6つ。
- 系統（Concept）に任意の `axis`（軸のID）を足す。どの分野の軸かは問わず、調査の中のいずれかの分野の軸のIDであること。
- 検証：軸のIDは分野の中で重複しない。中心の軸は分野ごとに多くとも1つ。系統の `axis` は存在する軸を指す。
- 点検：系統が1つ以上ある調査では、軸があり、中心の軸が1つあり、すべての系統が軸を持つこと。抜けはFillの対象にする。
- 画面：手法ツリーは中心の軸の系統から並べ、行の見出しに軸の名前を出す。

## 代替案

- 軸を新しいEntity型にする：一覧・差分・関係の端点など扱う箇所が多く、軸は分野に従属する少数の値なので過大。
- 軸を共通概念（Concept）の一種にし、系統を `instance_of` や `part_of` でつなぐ：Concept→Concept の関係は今の関係の端点に無く、系統と軸の区別も型で付かない。
- 系統の説明の文に書くだけ（0038の最初の実装）：構造として扱えず、並べ替えも点検もできない。

## 影響

- 任意の項目なので、今の調査とPatchはそのまま読める（schema_version 0.1.0のまま）。
- CodexのstrictなPatchのスキーマでは、任意の項目はnull可の必須項目になる（既存の扱いと同じ）。
- 軸の名前は分野ごとに自由に付ける。分野をまたいで軸を比べることはしない。

## 根拠

- [地図表現の研究動向](https://zenn.dev/epicai_techblog/articles/bfe50e2e0ad8ec)（2026-10-14に確認）：機能・推定対象・推定手法・処理構成・カメラの種類・地図表現・学習方式の軸で手法を分け、地図表現の変化で研究動向を並べる。
