# 0037: 10分の新規調査で論文50本を精読する

状態: Draft
日付: 2026-10-14 JST
対象タスク: 新規調査の時間と精読数、依頼ごとの時間の上限
関連ADR・受け入れ条件: [ADR 0025](../adr/0025-codex-app-server.md)、[0036](0036-codex-app-server.md)、[0034](0034-research-budget-and-checkpoints.md)。[0028](0028-eight-step-survey.md)・[0029](0029-four-wave-survey.md)の8手順4波を置き換える

## 目的と範囲

ユーザー指示（2026-10-14）：新規調査は全体で最大10分、その中で論文50本を精読する。依頼の種類ごとの上限は、違う視点の調査10分、深掘り調査10分、修正・補完1分、解説1分。

2026-10-13〜14の実推論では、新規調査は約16〜17分かかり、本文まで読めた論文は5〜10本だった。原因は2つ。1つの作業に6本を割り当て、1つのCodexが順に読んでいたこと。Mapが終わるまでExtractが始まらなかったこと。

実測（2026-10-14、ローカル、ChatGPTのログイン、gpt-6.1-sol）：1つの `codex app-server` のプロセスで20のthreadを同時に動かすと、論文1本を開いて要点と引用を返す作業は中央値30秒（最大39秒）で、プロセスのメモリは最大207MBだった。12並行・推論lowでは18〜32秒、172MB。1本1プロセスで並べると約105MBずつ増えるので、VPS（メモリ961MB）では1プロセスに多数のthreadを載せる。

## 現状と変更

新しい流れ（上限はすべて実行開始からの経過で決める）：

| 手順 | 内容 | 時間 |
|---|---|---|
| 1 Map | 全体像と論文50〜60本を挙げる。系統ごとに `submit_patch` で提出させる | 0〜210秒（150秒で書き出しを指示） |
| 2 Extract | 論文1本に1つのAgent。Mapが提出して保存された論文から、待たずに順に始める。同時に最大 `EXTRACT_CONCURRENCY`（既定16） | 1本あたり最大150秒。始められるのは400秒まで、終わりも400秒まで |
| 3 Explore | 抜けている観点と他分野の論文を探す。Mapの後、Extractと同時。保存された論文はExtractの順番待ちに加える | Mapの終了〜最大120秒 |
| 4 Synthesize | 課題の候補を階層にまとめ、手法の系統、ナレッジ、達成度を作る。チュートリアルは別Agentが同時に書く | 400〜490秒（Extractが早く終われば早く始める） |
| 5 Validate | サーバーの機械的な点検（スキーマと要件の未達）を、LLMが読んで、重要な抜けと埋め方（調査済みの情報から／検索）を決める | 最大25秒 |
| 6 Fill | Validateの抜けを、対象が重ならない組に分け、最大3つのAgentが同時に埋める | 終了の20秒前まで（最大60秒） |

- 全体の締め切りは600秒。各Agentの上限は「その手順の上限」と「締め切りまでの残り」の小さい方。最後の20秒はサーバーの統合と書誌の補完に使う。
- 1回の新規調査は1つのapp-serverプロセスを共有し、各Agentは別のthreadで動く。取消・終了ではプロセスごと止める。
- Extractの出力は、担当論文の要点（reading）と要旨の和訳（abstract_ja）、課題の候補、主な結果の主張と根拠。新しい論文は足さない（論文の発見はMapとExploreが担う）。サーバーは担当論文のreadingとabstract_jaだけを今の調査の論文に写すので、Extractが古い書誌を書いても、補完済みの書誌を上書きしない。
- 各Extractに渡す調査は、分野・課題・手法と担当論文だけに絞り、入力を小さくする。
- 読めなかった論文（時間内に順番が来ない、時間切れ）は、変更案の説明に本数を書く。

依頼の種類ごとの上限（判定を含め、依頼を受けてからの経過）：

| 依頼 | 上限 | 内訳 |
|---|---|---|
| 新規調査 | 10分 | 上の6手順 |
| 違う視点の調査・深掘り調査 | 10分 | 判定（最大20秒）、調査（残りから修正の90秒を引いた時間）、修正（残り） |
| 修正・補完 | 1分 | 判定、調査（残り）。修正のCodexは動かさず、検証エラーに挙がった操作を外して通れば使う |
| 解説 | 1分 | 判定、解説（残り） |

## 契約とデータ

- 保存するPatch、Commit、DSL、ブラウザとのAPIは変えない。手順の番号と名前（経過の表示、/lab）は6手順になる。
- `submit_patch` はMapとExplore、追記の調査が使う。ExtractとValidate、Synthesize、Tutorial、Fillは最終応答だけを使う。
- Validateの出力：`{gaps:[{target, field, why, fill:'existing'|'search', query}], message}`。Fillへはこの一覧を渡す。
- `EXTRACT_CONCURRENCY` でExtractの同時数を変えられる（VPSはメモリを見て決める）。

## 失敗と競合

- Extractの1本が失敗・時間切れでも、ほかは続く。失敗が90秒以内なら、締め切りに余裕がある限り1回だけやり直す。
- Map・Exploreの提出は保存のたびにExtractの順番待ちへ入る。同じ論文は1回だけ読む。
- Synthesize・Fillが失敗・時間切れなら、それまでの調査で変更案を作り、説明に書く。
- 取消：すべてのthreadを中断し、プロセスを止める。以降のAgentは始めない。
- 修正・補完の自動の取り外し：検証エラーに名前（ID）か位置が挙がった操作と、それを参照する操作を外して検証し直す（最大3回）。外した操作の数を説明に書く。

## 移行と運用

- VPSは `deploy/vps/compose.yaml` で `EXTRACT_CONCURRENCY` を指定する。
- 依頼の上限は `packages/agent/src/skills` の値と、`packages/agent/src/research-prompt.ts` の手順の時間で決まる。

## 検証と完了条件

- 単体：手順の時刻（Extractの開始の締め切り、同時数、Mapの提出からの開始、Exploreの論文の追加、締め切りによる上限の短縮）、Extractの結果を論文に写す処理、Validateの読み込み、Fillの組分け、自動の取り外し、依頼ごとの上限。
- 実推論（ローカル）：新規調査が10分以内に終わり、精読した論文の数を記録する（目標50本）。解説・修正・補完が1分以内、違う視点・深掘りが10分以内。
- VPS（SIWCの経路）：新規調査1回と解説1回。
- 必須チェック：Node24で `npm ci`、`npm run check`、`npm run check:deploy`。

## 未解決事項

- ChatGPTプランの同時実行の上限は未確認（20並行までは問題なし）。利用量の上限は実際に当たった：2026-10-14、この設計の試行3回（とその前の検証）の後、「You’ve hit your usage limit」で約3.5時間止まった。1回の新規調査は全体像・系統ごと（または偵察）・論文ごと・発散・統合・点検・補完で約70のAgentを動かし、それぞれが共通のルールを含む入力を読むため、プランの利用量を大きく使う。精読の本数（`TARGET_PAPERS`）と同時数（`EXTRACT_CONCURRENCY`）は、利用量とのかね合いで決める。
- 全体像が系統を提出しないことがある（2026-10-14の実推論で2回）。60秒で提出を促し、90秒までに無ければ5つの偵察が分野全体の論文を挙げ、各論文を読むAgentが手法と課題に位置づける。偵察が動いた後は、遅れて提出された系統に論文を挙げるAgentを付けない（利用量を抑える）。
- 1分の修正・補完で、Web検索の要る依頼がどこまでできるか。
