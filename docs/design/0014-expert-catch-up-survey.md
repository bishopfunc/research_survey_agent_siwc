# 0014: 専門家水準へのキャッチアップ調査（Prompt・DSL・画面）

状態: Implemented
日付: 2026-10-12 JST
対象タスク: P13
関連: [ADR 0010](../adr/0010-reuse-types-for-expert-survey.md)、[Codexの調査](0012-codex-research-modes.md)、[ナレッジ](0013-keywords-and-field-sources.md)、[アブストラクト](0011-paper-abstract.md)、[DSL調整ガイド](../dsl-schema.md)

## 目的と範囲

ユーザー指示（2026-10-12）による。調査の目的を「研究者が新しい分野に参入したとき、課題と既存研究を素早くキャッチアップし、ドメインの専門家に近い知識を身につけ、研究テーマを見つけること」とし、PromptとDSLと画面をそれに合わせる。DSLは複雑にしすぎない（ユーザー指示）。

重視する点（ユーザー指示）：

- ありきたりなものでなく、ドメインの専門家が知っていること
- 論文の記述をそのまま信じず、批判的に評価する
- 手法をそのまま並べず分類する
- 課題を分類し、ありきたりでなく重要なものを特定する
- 時系列で手法の網羅性を重視する
- 課題には論文で使われる英語表現をそのまま併記し、論文を引用しつつ達成度を定量的に示す
- 論文から貢献と5つの問い（どんなもの？・先行研究と比べてどこがすごい？・技術や手法のキモはどこ？・どうやって有効だと検証した？・議論はある？）を抽出する
- 学会・論文誌は略称で書く。アブストラクトは和訳する
- キーワードをナレッジ（参入者がキャッチアップすべき知識）とし、SOTA・モデル・ベースラインを加える
- 調査の最後に追加調査の候補を3つ出し、右のチャットで選べるようにする
- 論文の理解に必要なものと重要なFigを論文の詳細画面に出す

## 要求とDSLの対応

新しい型は作らない（[ADR 0010](../adr/0010-reuse-types-for-expert-survey.md)）。

| 要求 | 置き場所 |
| --- | --- |
| 課題の分類 | 既存のIssue.kind（本質的課題・部分課題・手法依存）とpart_of階層 |
| 課題の英語表現 | Issue.english_terms（任意、最大5、重複不可）。論文での言い方そのまま |
| 課題の達成度（定量） | 課題についてのClaim（aboutでIssueへ）。statementに数値・指標・ベンチマークや条件・論文、statusに未解決・一部解決・解決、scopeに条件、as_of、Evidenceに論文の結果の原文 |
| 批判的評価 | Claim.statusのdisputed、scopeの前提・制約、contradicts関係、論文の要点の「議論」 |
| 手法の分類 | 系統をConcept（説明に共通の考え方）で作り、Method→Conceptのinstance_ofでつなぐ |
| 時系列の網羅 | 各手法の提案論文の年・会議（既存）。系統ごとに古典から最新まで |
| 論文の貢献と5つの問い | Paper.reading（任意・null可）：contributions、novelty、key_idea、validation、discussion、key_figures。「どんなもの？」は既存のone_line_summaryが答える |
| 重要なFig | reading.key_figures（「Fig. N：何を示すか」）。画像はarXiv HTML版から表示（[0016](0016-paper-key-figures.md)） |
| アブストラクトの和訳 | Paper.abstract_ja（任意）。原文のabstractは置き換えない。原文が無い和訳は拒否 |
| 学会の略称 | Paper.venueの書き方（Promptの規則）。データ形式は変えない |
| ナレッジ | Keyword型のまま（型名は互換のため変えない）。画面の名前を「ナレッジ」にし、categoryにsota・modelを追加、baselineを再び作成対象に。SOTAは時点（Keyword.as_of）と論文が必須 |
| 追加調査の候補 | SurveyPatch.follow_ups（任意、最大3、各200字まで）。版のPatchに残るので、保存後もチャットに出せる |

重複の整理：論文が提案する手法・扱う課題はPaperのproposes・addressesだけで表し、同じ内容のRelationを作らない（Promptの規則）。既存データの重複は表示側で一つにまとめる（従来どおり）。

## Prompt

共通ルール（`survey-rules@2026-10-12T11:45+09:00`）の先頭を、出力の約束→目的と重視点（purpose）→批判的な読み方（critical）にした。続けて学会の略称（venue）、アブストラクトの原文と和訳（abstract）、課題（issues）、手法の系統（methods）、論文の要点（papers）、ナレッジ（knowledge）、重複の禁止（links）、最後の候補3つ（followups）を加えた。検証ルールの文に、新しい分類・SOTAの条件・和訳・readingの完全性・english_termsとfollow_upsの上限を加えた。

新規調査（`survey-new@…11:45`・`survey-discovery@…11:45`）は、サーベイで標準のデータセット・ベンチマーク・指標・ベースライン・モデル・SOTAを控え、一次論文の段階で課題を重要度で分類し、手法を系統ごとに古典から最新まで整理し、論文を批判的に読む。出力は課題4〜10（英語表現・難しさと重要性・達成度の主張）、系統3〜6、手法6〜15、論文8〜20（略称・原文と和訳・要点）、ナレッジ8分類、候補3つ。

追加調査（`survey-additional@…11:45`）に「分類・達成度・和訳の依頼は保存済みの情報から」の手順を加え、保存済みの調査に後から系統・達成度・和訳・要点を足せるようにした。キーワードの手順はナレッジに改めた。

出力が増えるため、実行上限を新規調査30分・追加調査20分に延ばした。

### レビューで直した点（2026-10-12）

3観点のレビュー（指摘を別Agentで反証）で見つかった点を直した。

- 作り話の防止：数値・実験結果を作らない規則を加えた。達成度の主張は、この実行で取得した文章に数値があるときだけ作り、根拠の原文に数値を含む文や表の行を写す。数値が無い課題は主張を作らず、messageに「未定量」と書く。例の数値（実在の論文の値で、しかも誤っていた）はプレースホルダの形に替えた。
- 論文の要点：取得した文章で書ける項目だけを埋め、ほかは空にする（readingの各項目は空でよい）。Figはその実行でキャプションを読んだものだけ。
- SOTA：意味に「リーダーボード等で確かめたか、調べた論文の中での最良か」を書き、as_ofは確認した日（調査日）。
- 保存済みの分析を消さない：既存項目を置き換えるときは、英語表現・和訳・要点を写す（keepstored、修正にも適用）。
- 修正の上限：新規調査15分・追加調査10分に延ばし、調査日を渡す。英語表現（空・重複・6件以上）、要点の空行、候補（重複・空・4件以上・200字超）は修正に回さず正規化で整え、要点が全部空ならnullにする。候補は重複不可。
- 画面：コレクション切替中に届いた調査開始・取消の応答を別のコレクションに出さない。実行中の調査があるコレクションを削除したらその調査を取り消す。別のコレクションの実行中に調査を押して409になっても、表示中の結果と「元に戻す」を消さない。保存時、候補から選んだ・入力した次の依頼を消さない。系統の見出しの件数を外した。論文の詳細で書誌（出版・引用数・コード・著者）をナレッジの後に移した。

## 画面

- 課題：カードと詳細に英語表現。詳細に「達成度」（主張の状態・内容・条件・時点。押すとその主張へ）。主張が無ければ「未調査」。カードには最新の達成度を1件。
- 手法タブ：既定を「系統」表示にし、系統ごとに手法を年順に並べる（年・名前・会議・説明1行）。系統の無い手法は「未分類」。従来の系譜ツリー・代表論文も残す。手法の詳細に系統のチップ。
- 論文の詳細：理解に必要な順に、著者・年・会議、どんなもの、要点（貢献・新規性・キモ・検証・議論・重要なFig）、代表Fig、アブストラクト（和訳を先に、原文へ切り替え）、主張と根拠（根拠の原文の抜き書き）、使われるナレッジ、書誌・引用数・コード、つながり図。要点が無ければ「要点 未作成」。
- ナレッジタブ：8分類の見出し（データセット・ベンチマーク・ハードウェア構成・シミュレータ・評価指標・SOTA・モデル・ベースライン）。時点のあるもの（SOTA）は「YYYY-MM-DD時点」。
- チャット：最新のCodexの回答（保存前の変更案、または保存済みの最新版）の下に候補3つ。押すと入力欄に入る。実行中は出さない。
- 編集フォーム：英語表現（1行に1件）、和訳、要点（6項目）、ナレッジの時点を編集できる。要点を全部空にするとnull。

### 追記：既存の調査と読み直しの確認（2026-10-12）

- P13より前に作った調査や、Codexの候補が無い調査では、チャットの候補に、足りないものを補う追加調査の依頼を最大3つ出す（手法の系統、課題の達成度、和訳と要点、英語表現の順）。押すと入力欄に入る。Codexの候補があればそちらを優先する。
- 調査にある論文の保存済みの情報で依頼に足りないとき、Codexは読み直さず、候補の1つを「その論文を読み直して補う」依頼にする。ユーザーがそれを送ることを読み直しの承認とする（共通ルール library、`survey-rules@2026-10-12T12:00+09:00`）。

## 失敗と互換

追加した項目はすべて任意で、schema_versionは0.1.0のまま。既存のsnapshot・版・Patchはそのまま有効。旧分類（task・concept・method・other）は表示だけ残す。Codexの出力では、follow_upsの空・null・4つ以上を正規化で整え（最大3・空を除く・200字まで）、readingなどnull可の項目はnullを残す。

## 検証と完了条件

- 検証：english_termsの上限と重複、和訳には原文、readingの各項目（空でよい、貢献の各行は空不可）またはnull、SOTAの時点と論文、時点の日付形式、新分類、Patchのfollow_upsの上限と空文字。
- Codexの出力スキーマ：strict（全項目required・追加禁止）のまま、readingはFigと同じ$defs参照＋null。
- Prompt：目的と重視点が先頭、各規則の文、候補3つ、実行上限。
- 系統：系統ごと・年順・未分類が最後、複数の系統に属する手法は両方に出る。
- 変更なしのrunでも候補3つを返す。
- 画面：サンプルで課題の英語表現と達成度、系統表示、論文の要点、ナレッジ8分類、候補3つ、編集フォームをヘッドレスChromeで確認する。
