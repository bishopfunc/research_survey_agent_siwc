# 0027: 論文ごとの課題の抽出と統合、精読の割り当て

状態: Implemented（ローカルPoC、モック試験のみ）
日付: 2026-10-12 JST
対象タスク: P29
関連: [0021 論文DBと段階実行](0021-paper-db-and-staged-runs.md)、[0025 事実と出典](0025-facts-and-sources.md)

## 背景

ユーザー指示（2026-10-12）：課題の階層化が不十分。論文1本ずつから課題を事実と出典として取り出してから統合しているか。「LLM推論：誘発・探索・学習・検証の研究地図」の結果に漏れが多いのはなぜか。

実行記録（`.poc/runs/72be54fc-…`）を調べた結果：

1. 精読の割り当てで系統がまるごと落ちた。作業は系統単位で論文を詰め、各作業の先頭5本だけを精読したため、同じ作業に入った2番目以降の系統（強化学習の4本など）は誰も読まなかった。
2. 課題は全体像の段階でページを開かずに作られ、その後変わらない。深掘りは他の項目を変えるなと指示され、サーバーも論文以外の置換を捨て、統合は課題の置換を任意にしていた。論文ごとに課題を出典つきで取り出す段階が無い（結果は深さ2、part_ofは1本）。
3. 実行したサーバーが約3時間前の起動で、文献ガイド・チャレンジの節・事実と出典が反映されていなかった（運用の問題。サーバーを起動し直す）。
4. 全体像の論文が20〜40本、精読が5本×3作業、統合に追加の論文の枠が無い。

## 変更

### 精読の割り当て

- 系統（instance_of）ごとに論文を全体像の順（重要な順）に並べ、系統を作業に配る。各作業は自分の系統から1本ずつ順番に（ラウンドロビンで）選び、上限まで精読する。どの系統も最初の1本は読まれる。
- 作業数を3→4、1作業の精読を5→6本にし、深掘りの上限時間を270→360秒にする。
- 上限で1本も読めなかった系統はmessageに書く。

### 論文ごとの課題の抽出（深掘り）

- 深掘りの作業は、精読した論文ごとに、その論文が取り組む問題（序論の問題設定・「しかし〜が難しい」の段落・認める限界）を課題の候補として出す：`add_entity` のIssue（種類・英語表現・一文の説明）と、その論文から写した出典（Evidence、origin＝論文）。候補は論文をまたいでまとめず、part_ofも付けない。
- サーバーは深掘りで追加されたIssueを候補として記録する（新しい型は作らない）。

### 課題の統合（統合）

- 統合の指示に候補のIDを渡し、同じ問題を指す候補を1つの課題にまとめ、候補の出典をすべてその課題のevidenceに入れ、part_of（下位の問題）とspecializes（特殊な場合）で、文献が支える限り3階層以上（分野の本質的な課題→中位の課題→論文が取り組む具体的な課題）にする。全体像の課題はIDを保って置き換えてよい。
- サーバーの後処理：
  - 出典がすべてほかの課題に引用された候補は、まとめられたものとして消す（関係と、論文・文献・ナレッジ・チュートリアルからの参照も外す）。まとめられなかった出典つきの候補は課題として残す。出典の無い候補は消す。
  - 課題のevidenceが論文を出典元とするとき、その論文のaddressesにその課題を足す（課題と論文のつながりを出典から作る）。
  - 後処理の結果が検証に通らなければ後処理をしないで残し、messageに書く。

### 全体像

- 論文は30〜60本挙げ、サーベイや入門のページを2つ以上開いて文献ガイドにし、論文の一覧はその目次や分類から取る（記憶から挙げない）。上限時間を330→420秒にする。

## 検証

- モック試験：系統のラウンドロビンでどの系統も1本は読まれること、上限を超えた系統がmessageに出ること、候補のまとめと削除・残す規則、addressesの導出、後処理が検証に通らないときに元のまま残すこと、Promptの規則。
- 未確認：実Codexでの課題の階層の深さと、網羅（漏れ）の改善。網羅を確かめる批評の段階（期待される領域のチェックリストとの照合）は今回入れない（次の候補）。
